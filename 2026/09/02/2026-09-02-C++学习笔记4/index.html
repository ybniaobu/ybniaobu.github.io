第十七章 智能指针与内存管理

之前的例子中，对动态内存的管理都是通过 new 和 delete 来手动管理的。然而，手动管理动态内存很容易出问题，因为确保在正确的时间释放内存是相对困难的：如果忘记调用 delete，被分配的内存就无法归还给系统，从而产生内存泄漏 memory leak；如果释放得过早，指针就会变成指向已销毁对象的悬空指针 dangling pointer；如果对同一块内存释放两次，还会发生二次释放 double free。而悬空指针与二次释放都属于未定义行为 undefined behavior，轻则导致程序崩溃，重则破坏数据、引发难以排查的安全漏洞。此外，若在 new 之后、对应的 delete 之前抛出异常，释放内存的语句将永远无法执行，同样会造成内存泄漏。可见，仅仅依靠 new/delete 来手动管理内存，既不安全，也不省心。

为此，C++ 11 标准库引入了智能指针 smart pointer。智能指针在行为上类似内置指针，但它的核心价值在于可以自动管理所指向对象的生命周期：借助后面将要介绍的 RAII 思想，当智能指针对象被销毁时，它会自动释放所管理的内存，使程序员无需（也不应）再手动调用 delete。C++ 11 一共提供了三种智能指针（位于头文件 <memory> 中）：独占对象所有权的 unique_ptr、可共享对象所有权的 shared_ptr，以及配合 shared_ptr 使用、不增加引用计数的 weak_ptr，它们分别适用于不同的所有权模型。

RAII 思想

资源获取即初始化 resource acquisition is initialization (RAII) 是一种借助对象的生命周期来管理资源的编程思想，简单来说就是一句话：在构造函数中获取资源，在析构函数中释放资源。只要把某份资源的生命周期绑定到一个局部对象的生命周期上，那么无论该对象是正常离开作用域，还是因异常触发栈展开而被销毁，其析构函数都一定会被执行，资源也就一定能得到释放，程序员无需手动触发。其中的资源 resource 是一个相当宽泛的概念，包括：动态内存、文件句柄、互斥锁、数据库连接、网络套接字等。下面用一个简单的例子来演示 RAII 的工作方式：

unique_ptr

std::unique_ptr 用于管理动态分配对象的生命周期，其实例拥有所指向对象的独占所有权 exclusive ownership，不允许拷贝构造或拷贝赋值，但支持移动语义，即所有权可以通过 std::move 转移。当实例被销毁，即离开作用域或被显式重置时，它会调用删除器 deleter（默认使用 delete）释放所管理的对象，允许用户提供自定义删除器。unique_ptr 是首选智能指针，常用于替代裸指针，内部也通常只存储一个裸指针，并持有一个删除器实例（默认删除器无状态，不占额外空间）。

shared_ptr

std::shared_ptr 与 unique_ptr 的独占模型不同，多个实例可以共同拥有并管理同一个对象，即共享所有权 shared ownership。其实现依赖引用计数 reference counting，即每个被管理的对象都关联着一个计数，记录当前有多少个 shared_ptr 指向它，每通过拷贝或赋值新增一个共享该对象的 shared_ptr，引用计数加一；每销毁或重置一个，计数减一；当计数归零，即不再有任何 shared_ptr 指向该对象时，对象才会被自动释放。

引用计数存放在一块单独分配的控制块 control block 中，因此 shared_ptr 内部通常保存两个指针，一个指向所管理的对象，一个指向控制块。控制块由第一个接管对象的 shared_ptr 创建，其中一般包括：

  1. 强引用计数 strong reference count：记录当前有多少个 shared_ptr 共享该对象，归零时销毁对象，但控制块本身未必随之释放；
  2. 弱引用计数 weak reference count：记录指向该对象的 weak_ptr 数量，强计数与弱计数都归零时控制块才会被真正释放（详见后文 weak_ptr 一节）；
  3. 删除器 deleter：销毁对象时使用的可调用对象，默认是 delete，允许用户自定义；
  4. 分配器 allocator：若用户提供了自定义分配器，也一并保存在控制块中；
  5. 指向所管理对象的指针（或对象本身）：从裸指针构造时，控制块只存指向对象的指针。使用 make_shared 创建时，对象与控制块位于同一次分配中，此时控制块内直接包含对象本身。

②循环引用 circular reference 问题：
引用计数无法处理循环引用，若两个对象各自持有指向对方的 shared_ptr，它们的引用计数永远无法归零，即使外部已没有任何指针可达，这两个对象也不会被释放，从而造成内存泄漏。解决办法是把其中一环换成不增加引用计数的 weak_ptr，这正是下一小节要介绍的内容。

③线程安全性：
shared_ptr 的线程安全是有条件的，主要保证的是控制块内部的引用计数操作。引用计数的增减是原子的，即多个线程分别持有指向同一对象的 shared_ptr，各自独立地进行拷贝、析构或 reset() 时是安全的，计数不会出错，对象也只会被释放一次。但被管理的对象本身并不是线程安全的，多个线程同时通过 shared_ptr 读写同一个对象仍需加锁或使用其他同步手段。此外，同一个 shared_ptr 实例被多个线程同时读写是不安全的，需要借助互斥锁等保证同步，正确做法是各线程先拷贝出属于自己的那份 shared_ptr 再使用。

weak_ptr

std::weak_ptr 是一种不控制对象生命周期的智能指针，表示对某个由 shared_ptr 管理的对象的弱引用，但不增加其强引用计数，常用于打破 shared_ptr 之间的循环引用。其内部同样保存指向控制块的指针，但它只增加控制块中的弱引用计数。由于对象可能已被销毁，weak_ptr 不提供 * 和 -> 访问对象，必须通过成员函数 lock() 尝试提升为 shared_ptr，成功时返回非空 shared_ptr 并可安全访问，强引用计数 + 1，失败时返回空 shared_ptr。

new / delete

在之前的笔记中已经介绍过 new / delete 的基本用法，这里再深入到它们背后的机制。一个 new 表达式实际上完成了两件事：①调用名为 operator new 的函数，向系统申请一块足够大的原始内存 raw memory；②在这块内存上调用对象的构造函数完成初始化。与之对应，一个 delete 表达式同样分为两步：①先调用对象的析构函数完成清理；②再调用名为 operator delete 的函数把内存归还给系统。

因此需要区分两组概念：new / delete 是 C++ 的关键字，由它们构成的 new 表达式与 delete 表达式属于运算符，负责把分配与构造、析构与释放组合在一起。而 operator new / operator delete 是函数，标准中分别称为分配函数 allocation function 与释放函数 deallocation function，它们按作用域分为两类：①全局版本，写作 ::operator new / ::operator delete，标准库为它们提供了一份默认实现，同时标准也允许用户把它替换掉；②类内重载的版本，作为该类的静态成员函数，只作用于这个类的 new / delete 表达式。真正向系统申请和归还内存的始终是这两个函数，new / delete 表达式不过是它们与构造函数、析构函数调用的组合。

分配释放函数虽然在 <new> 头文件中，但常规形式不需要包含 <new> 也能使用，因为标准规定普通版本、数组版本以及 C++ 17 起的对齐版本（即不带 nothrow / placement 额外参数的几种）会在每个翻译单元中被隐式声明。

分配器

std::allocator<T> 是 C++ 标准库中的默认内存分配器 allocator，定义在 <memory> 头文件中。它将内存分配与对象构造两个步骤分离：先分配原始内存，再在其上调用构造函数；销毁时先调用析构函数，再释放内存。而 new 将内存分配和对象构造组合在了一起，delete 将对象析构和内存释放组合在了一起。STL 容器（如 vector、list）默认使用该分配器，但也允许用户传入自定义分配器，以满足特定的内存管理需求，例如使用内存池、共享内存或跟踪内存分配统计等。

C++ 17 引入 std::pmr::polymorphic_allocator（位于 <memory_resource>），允许在运行时指定内存资源，适合构建内存池等复杂系统，属于更高级的内存管理技术。

第十八章 字符串与 I/O 流

字符串

C++ 中的字符串处理主要依靠标准库提供的专门类型，而不是 C 风格字符串（已在第二章类型、变量与声明的字面量小节中详细讨论过）。后者需要手动管理内存，容易出现忘记结尾空字符 '\0'、缓冲区溢出、越界访问等问题。为此，标准库在头文件 <string> 中定义了一个通用的字符串模板 std::basic_string，并为常用的字符类型分别准备了别名，如下表：

std::u32string std::basic_string<char32_t> char32_t
std::u8string std::basic_string<char8_t> char8_t（C++ 20 起）

由于在绝大多数场景中，使用的都是 std::string，它和 C 风格字符串兼容，也可以存储 UTF-8，故下面主要介绍 std::string 以及用于高效访问字符串数据的字符串视图 std::string_view。

string

std::string 是 std::basic_string<char> 的类型别名，表示由 char 组成的动态字符序列，它的字符在内存中连续存储（C++ 11 起由标准保证），内存由对象自动管理、按需扩容，因此可以将其理解为字符向量 vector<char>，只是说它保证在序列末尾额外存放一个 '\0'，并提供了大量字符串专有的操作。与 vector 一样，在发生扩容或插入、删除后，原有的迭代器、指针与引用都可能失效。此外，std::string 内部通常还实现了短字符串优化 short string optimization (SSO)，当字符串很短时，字符直接存放在对象自身的内部缓冲区中，不进行堆分配，从而避免小字符串频繁申请内存，只在字符串较长时才把字符转移到堆上。

标准流

标准库在头文件 <iostream> 中包含了 <istream> 和 <ostream>，分别定义了两个类模板：输入流 std::basic_istream 与输出流 std::basic_ostream，并为常用的字符类型提供了别名，如 std::istream / std::ostream（对应 char）以及 std::wistream / std::wostream（对应 wchar_t）。向流中写数据使用 << 插入运算符 insertion operator，从流中读数据使用 >> 提取运算符 extraction operator，二者都返回流对象自身，因此可以连续串联，例如 std::cout << a << b;。同时，在 <iostream> 中预先定义好了若干个与标准输入输出设备绑定的全局流对象，如下表：

std::cerr 标准错误，不带缓冲，立即刷新，类型为 std::ostream
std::clog 标准错误日志，带缓冲，类型为 std::ostream

这些标准流对象是 RAII 的典型例子：它们都是定义在 <iostream> 中的全局对象（在 main 开始之前就已完成构造），构造时取得设备与缓冲区等资源，析构时释放资源，即刷新缓冲区、把尚未真正写出的数据交给操作系统并回收缓冲区内存。它们的析构发生在程序正常结束、全局对象被销毁之时，因此只要程序正常退出，缓冲区中残留的数据都会被自动写出。反之，若程序通过 std::abort() 等非正常方式终止，这些全局对象不会析构，缓冲区也就不会被刷新。

std::endl 会写入换行符 '\n' 并刷新缓冲区，而直接写 '\n' 只换行、不刷新。频繁刷新会拖慢输出，因此大量输出时更推荐用 '\n'，只在确需立即看到结果时才用 std::endl。

缓冲区

流内部维护着一块称为缓冲区 buffer 的内存区域：输出时，写入流的数据并不会立刻送达设备，而是先暂存进缓冲区，等缓冲区被填满、被显式刷新或程序正常结束时，才一次性交给操作系统真正写入设备。输入时则相反，一次从设备读入一大块数据塞进缓冲区，之后的读取操作直接从缓冲区中取用，取空后再去读下一块。之所以这样做，是因为设备访问（磁盘、终端、网络等）远比内存操作慢，把大量零散的小块读写合并成整块的读写，可以减少系统调用次数，从而提升效率。

缓冲区本身并不由流对象直接管理，而是交给独立的流缓冲区 streambuf（std::basic_streambuf）负责，流对象内部只保存一个指向它的指针，文件流底层用的是 std::basic_filebuf，字符串流底层用的是 std::basic_stringbuf。流对象通过成员函数 rdbuf() 可以取得当前流关联的 streambuf。

range

C++ 20 之前，标准库算法只能用一对迭代器来表达一段序列，写法较为啰嗦。C++ 20 引入了范围 range，对算法和迭代器库进行了扩展与泛化，提供了更加简洁安全的接口，主要头文件是 <ranges>，命名空间为 std::ranges。这次扩展建立在 C++ 20 新增的模板概念 concept 之上，即用编译期谓词对模板参数提出明确要求。此前的算法都是无约束算法 unconstrained algorithm，模板参数只有名字、要求仅写在文档里，一旦传错类型，错误会在算法内部深处爆发，报错冗长难读。C++ 20 据此在 std::ranges 中提供了使用概念约束的算法 constrained algorithm（如 std::ranges::sort），把要求写进签名，不满足时直接在调用处报错，接口也顺带由迭代器对改成了范围。两版算法并存，无约束版本仍保留在 <algorithm> 中。

ranges 大致包含以下三部分内容：

  • 范围概念 range concept：<ranges> 头文件中定义了很多范围的概念，用于描述范围的属性（诸如长度、迭代器类型等），算法与视图正是借助这些概念来约束各自所能接受的范围；
  • 视图 view：视图是查看范围的一种方式，它提供了一种惰性求值、可组合、轻量级的方式来处理序列数据，支持管道操作符 | 串联组合；
  • 使用概念约束的算法 constrained algorithm：前缀为 std::ranges:: 的算法，仍然位于 <algorithm> 头文件中（数值版本位于 <numeric>），接口由迭代器对改为范围，并额外支持投影。

第二十章 并发与线程

前面各章的程序基本都是单线程的：整段程序只有一条执行流，语句按书写的顺序一条接一条地执行。然而如今的计算机几乎都是多核的，如果程序始终只用一条执行流，就等于让大部分核心闲置。为此，C++ 11 在标准库中引入了一整套并发 concurrency 与多线程 multithreading 设施，让程序可以同时推进多个任务，从而充分利用多核处理器、提升吞吐量，并让交互式程序在执行耗时操作时仍保持响应。但并发并非免费的午餐，多条执行流若同时访问同一份数据，就可能引发难以复现的错误。由于是基础笔记，本章以梳理概念与常用设施的整体脉络为主，介绍每项设施时也会说明它究竟要解决什么问题，至于底层实现与高级用法则不深入展开。

标准库的并发设施分散在若干头文件中：线程 <thread>、互斥量 <mutex>、条件变量 <condition_variable>、原子类型 <atomic>、异步任务 <future>，C++ 20 又补充了闩锁 <latch>、屏障 <barrier>、信号量 <semaphore>。

并发的基本概念

①进程与线程
进程 process 是操作系统进行资源分配的基本单位，每个进程拥有自己独立的地址空间、文件描述符表等资源，进程之间彼此隔离，一个进程崩溃通常不会影响另一个。线程 thread 则是 CPU 调度的基本单位，一个进程内可以包含多个线程，它们共享该进程的地址空间与大部分资源，但各自拥有独立的栈、程序计数器与寄存器等执行上下文。

②并发与并行
这两个词经常混用，但含义不同：并发 concurrency 强调的是多个任务在同一时间段内交替推进，宏观上像同时进行，微观上可能只是快速切换。而并行 parallelism 强调的是多个任务在同一时刻真正同时执行，必须依赖多核等硬件条件。可以说并行是并发的一个子集，单核 CPU 上也能实现并发（通过分时切换），但无法实现真正的并行。反过来，多核加上多线程只是具备了并行的条件，至于任务是否真的并行，还要看具体的调度与实现。程序可用的并行线程数取决于硬件的并发支持能力，可以通过 std::thread::hardware_concurrency() 查询（返回的是提示值，可能为 0 或不够精确），它通常等于逻辑核心数，可作为创建线程数量的参考上界。

③上下文切换
单个 CPU 核心同一时刻只能执行一条指令流，因此要在单核上并发运行多个线程，就必须在它们之间快速切换，保存当前线程的执行上下文并恢复另一个线程的上下文，这一过程称为上下文切换 context switch。切换本身有开销，且会打断 CPU 流水线与缓存局部性，所以线程并非越多越好。

④内存模型
内存模型 memory model 是硬件或编程语言对内存操作的抽象规范，尤其规定多线程环境下内存读写操作的可见性 visibility、原子性 atomicity 和有序性 ordering。这三条性质都源自现代计算机读写内存的实际过程：数据平时存放在内存 memory 中，CPU 需先把它加载到缓存 cache，再读入寄存器 register，在寄存器中完成运算后写回缓存，最后才由缓存写回内存。其中缓存并非所有 CPU 核心共有，L1、L2 通常每个核心私有，L3 一般多个核心共享，因此同一变量在多个核心中可能各存一份副本。由此带来三个问题：①可见性，指一个线程对共享变量的修改，另一个线程能否、何时能看到，由于修改是在某个核心的寄存器中完成后才逐级写回，写回内存的时刻可能被推迟，其它核心的缓存副本也不会自动同步、可能仍是旧值，因此新值未必立刻可见；②原子性，指一个操作能否不被打断地完整执行，其它线程观察到的只有”没做”与”做完”两种状态，像 ++counter 实际上由读取、加一、写回三步组成，其它线程完全可能插入其中，读到尚未写回的结果；③有序性，指代码书写顺序与内存操作实际生效的顺序是否一致，出于性能考虑，编译器与 CPU 都可能进行指令重排 instruction reordering，这在单线程中通常无害，多线程中却可能导致一个线程读到旧值、默认值，甚至看到未完全初始化的对象状态。

join 与 detach

std::thread 对象与它管理的线程之间有两种收尾方式，必须选择一个，即必须 join() 或 detach()，否则 std::thread 对象在析构时仍然 joinable()，程序就会直接调用 std::terminate 终止。

成员函数 说明
join() 阻塞当前线程，直到目标线程执行完毕，随后该对象不再关联任何线程
detach() 使目标线程在后台独立运行，此后该对象不再与之关联，也无法再等待它
joinable() 判断该对象当前是否关联着一个尚未收尾的线程

jthread

由于 std::thread 需要手动 join / detach，可能会因为忘记导致程序意外终止。为此，C++ 20 引入了 std::jthread，作为 std::thread 的升级版，在保留其大部分接口的同时，新增了两个特性：析构时自动 join 和协作式停止机制，旨在让线程管理更安全和简洁。因此 C++ 20 之后的代码中若没有特殊理由，应优先使用它。

自动 join

std::jthread 的析构函数在对象销毁时会自动完成两件事：①若此前尚未请求停止，则先调用 request_stop() 发出停止请求；②若仍然 joinable()，则调用 join() 等待线程结束。因此它不会再像 std::thread 那样因忘记收尾而让程序 std::terminate，也无需再写 if (t.joinable()) t.join(); 之类的样板代码。std::jthread 跟收尾有关的成员函数跟 std::thread 是一致的，就不再重复了。

自动收尾其实正是第十七章介绍的 RAII 思想在线程上的应用：构造 std::jthread 时获取资源，即启动线程，析构时释放资源，即请求停止并等待线程结束，把线程的收尾工作绑定到了对象的生命周期上，因此无论函数是正常返回还是因异常触发栈展开，线程都一定会被正确收尾，程序员无需、也不应再手动处理。一个简单的示例如下，注意它无需任何手动收尾：

协作式停止

std::jthread 内置的停止机制是协作式 cooperative 的，即 request_stop() 只是发出一个停止请求，并不会强行杀死线程，线程是否响应、何时响应，完全由线程自己决定。这既符合线程无法被安全强杀的事实，也给了线程清理资源、保存状态的机会。

避免数据竞争

数据竞争 data race 指两个或多个线程在同一时间段内访问同一处共享数据，其中至少有一个访问是写操作，且这些访问之间没有任何同步手段来确定先后顺序。数据竞争属于未定义行为 undefined behavior，其后果无法预测，可能表现为计算结果错误、数据损坏甚至程序崩溃。最典型的例子是一个计数器，++counter 看似是一条语句，实际上由读取、加一、写回三步组成，两个线程交错执行时，一方的写回可能覆盖另一方的结果，导致最终值小于预期：

理论上避免数据竞争的最佳方式就是不共享数据，把数据保存在只由本线程访问的局部变量、堆对象或 thread_local 变量中。但在多数情况下，数据总要在多个线程之间共享，这时就离不开各种同步 synchronization 手段，本章后面几节正是围绕它们展开的：互斥量 mutex 把访问共享数据的代码保护成临界区 critical section，即一块只能被串行访问、不允许并发读写共享数据的代码区域，以保证同一时刻只有一个线程能够进入；条件变量 condition variable 在此基础上提供等待通知的机制，让线程可以休眠着等待某个条件成立，而不必反复加解锁轮询；原子操作 atomic operation 则更进一步，对于单个简单变量，无需加锁就能保证对它的操作不可分割。

thread_local

线程局部存储 thread local storage 用关键字 thread_local 声明，它是一个存储类说明符 storage-class specifier，表示该变量在每个线程中各有一份独立实例，线程首次使用时初始化，线程结束时销毁。

对于块作用域 thread_local，它类似 static 局部变量：只在第一次执行到声明时初始化一次，但生命周期持续到线程结束，而不是函数结束。若存在线程池的线程复用，thread_local 状态可能在多个任务之间保留，若希望每个任务独立，需要手动重置。

另外，thread_local 变量还可以作为类静态数据成员，每个线程访问时，看到的是该线程自己的副本。

volatile

这里顺便简单介绍一下 volatile 关键字，它是一个类型限定符 type qualifier，与 const 一样用于修饰变量，它告诉编译器：这个变量可能被外部随时改掉，别优化掉读写（如缓存到寄存器、消除重复读取等），确保直接从内存地址访问数据。它主要用于硬件寄存器映射、信号处理、中断处理程序等场景中。但在多线程共享数据时，‌它不能替代原子操作和同步机制‌，不建立线程间的可见性与顺序保证‌。它常被误认为与 Java 中同名关键字语义相近，但在 C++ 中二者完全不同，C++ 的 volatile 与多线程无关。

互斥量

互斥量/锁 mutex（取自 mutual exclusion）是一种常用的同步原语，用于保护对共享资源的访问，确保同一时间只有一个线程或任务能够访问该资源。它不仅能防止数据竞争，还通过 lock() / unlock() 建立线程间的同步关系，使临界区内的写入对后续获得锁的线程可见。

原语可以理解为由‌操作系统或编程语言提供的最基本操作、基本构件或基本机制。

mutex

std::mutex 是最基本的互斥量，同一时刻只允许一个线程持有它，因此它只有加锁、解锁两种状态。当一个线程调用 lock() 成功时，该线程就成为了互斥量的持有者。此时，若其它线程调用 lock() 就会被阻塞，即被挂起、让出 CPU 进入等待，直到持有者调用 unlock() 释放锁后才被唤醒并重新尝试加锁。正是这一约束保证了互斥：被 lock() / unlock() 夹起来的临界区永远只有一条线程在执行，不会出现两个线程同时读写同一份数据的情形，这就是它避免数据竞争的根本原因。此外，unlock() 与其它线程随后的 lock() 之间还建立了同步关系，使前一持有者在临界区内的写入对后一个持有者一定可见，因此互斥量在排除并发访问的同时，也保证了共享数据的可见性。它的主要成员函数如下：

成员函数 说明
lock() 加锁，若已被占用则阻塞等待，直到成功
try_lock() 尝试加锁，成功返回 true，已被占用则立即返回 false
unlock() 解锁，必须由持有该锁的线程调用

使用 std::mutex 要注意几点：①同一线程重复 lock() 或 try_lock() 属于未定义行为，实践中通常表现为死锁；②互斥量必须在任何线程访问它之前完成构造，并在所有线程都不再访问它之后才析构，销毁一个仍被锁定或仍有线程等待的 std::mutex 是未定义行为；③线程也不能在持有互斥量时终止。

RAII 锁管理器

直接手写 lock / unlock 比较危险，若中途抛出异常或提前返回，unlock 就可能被跳过，锁永远不释放，其它线程将一直阻塞。因此实际代码中几乎不应该直接调用它们，而应交给标准库提供的几个 RAII 风格的锁管理类自动管理，它们构造时加锁、析构时自动解锁，即使发生异常也能保证锁被释放。

条件变量

在多线程编程中，经常需要一个或多个线程等待某个条件成立，并由其他线程在条件可能成立时通知它们，例如消费者线程要等队列里有数据了再取，生产者线程要等队列有空位了再放。这类等待如果使用简单的轮询，比如循环检查条件，会浪费 CPU 资源，又难以保证及时性。为此，标准库提供了条件变量 condition variable，配合互斥量组成经典的阻塞/唤醒机制：线程在条件不满足时阻塞，当条件可能满足时，由其他线程唤醒。

C++ 11 在头文件 <condition_variable> 中提供了两个条件变量类型 std::condition_variable 和 std::condition_variable_any。这两个条件变量类型配合的互斥量都必须有手动加解锁的能力，即可以调用 lock() 和 unlock()，因为等待期间需要暂时释放锁，被唤醒后再重新加锁。std::condition_variable 只能与 std::unique_lock<std::mutex> 配合使用，而 std::condition_variable_any 通常配合 std::shared_mutex、std::shared_lock 或自定义锁使用。它们常用的成员函数如下：

原子操作

原子操作 atomic operation 指在多线程环境中不会被线程调度机制打断的操作，其执行过程不可分割，要么完全执行，要么完全不执行，不会出现中间状态，是不用加锁就能避免数据竞争的手段，也是无锁编程 lock-free programming 的基石。所谓无锁编程，指完全不使用互斥量等阻塞式同步手段，只依靠原子操作（配合内存序）来协调多个线程对共享数据的访问，从而避免加锁带来的阻塞、死锁与上下文切换开销。但二者并不等价，使用了原子类型并不意味着程序就是无锁的，若某平台上原子操作无法由硬件指令直接实现，标准库仍可能借助内部互斥量来模拟原子性，此时写法上虽未加锁，底层却依旧会上锁，可用 is_lock_free() 判断。

比较并交换 CAS

比较并交换 compare-and-swap (CAS) 主要解决的是多线程里最常见的读改写竞争问题，简单来说就是如果这个值还是刚刚看到的旧值，就把它改成新值，否则就说明其它线程修改了，此时放弃修改并拿最新值重试。也就是上面提到的 compare_exchange_weak 与 compare_exchange_strong 的行为，若当前值与 expected 相等，就把 desired 写入并返回 true，否则把当前实际值写回 expected 并返回 false。对于 compare_exchange_weak 最常用的使用方式是循环重试：

内存序

前面介绍内存模型时已经提到，多线程共享数据时存在可见性与有序性两方面的问题，而这两者恰恰是原子操作本身无法保证的，原子操作只保证单个操作不可分割，即只解决原子性。它既不阻止编译器与 CPU 出于性能考虑对指令进行重排，也不保证一个线程的写入能立刻被另一个线程看到。为此 C++ 内存模型引入了内存序 memory order，告诉编译器与 CPU 哪些内存访问不得被重排到某条原子操作的某一侧，以及一个线程在原子操作之前的写入在什么条件下对观察到该原子操作的其它线程可见。C++ 定义了六个内存序枚举，如下表：

异步任务

前面几节讨论的都是线程层级的东西，std::thread 直接对应一条系统线程，我们关心的是怎么创建它、怎么同步它、怎么保护共享数据。但实际写程序时，直接用线程太底层，会分散写实际业务的注意力，更多时候我们想表达“这里有一件耗时的活，先交出去，等我要结果的时候再拿回来”，这就是异步 asynchronous 的概念。把这种“活”从调用流程里独立出来，就称为任务 task。一个任务可以理解为一件可以被独立调度并且将产生一个结果的事情，它通常包含三部分：要执行的可调用对象、执行状态（尚未开始/正在执行/已完成）、结果或异常。而 C++ 11 引入的 std::async / std::future / std::promise / std::packaged_task 这一整套设施（位于 <future> 头文件中），提供了任务级的异步抽象，把程序员从管理线程提升到管理任务，从而能以更简洁、也更安全的方式处理异步操作。

async

std::async 是启动异步任务最直接的方式：它接收一个可调用对象及其参数，启动一个任务（可能异步执行，也可能延迟到取值时执行），并立即返回一个 std::future 对象，future 表示一个异步结果的句柄，可以先继续做其它事情，需要结果时再调用 get() 取值，例如：

另外，std::async 返回的 future，如果未 get() 或 wait() 就析构，且任务是 async 策略，析构可能阻塞直到任务完成。跟 std::thread 一样，std::async 默认按值拷贝/移动参数，若要传引用，用 std::ref / std::cref。

future

std::future 表示一个异步结果的句柄，它本身并不存放结果，而是关联着一份由实现维护的共享状态 shared state：结果或异常就存放在其中，此外还有一个标记该状态是否就绪的标志。按照标准，一份共享状态至多只能与一个 std::future 关联，因此它不可拷贝、只能移动，并且一个 std::future 只能取用一次。其常用的成员函数如下：

成员函数 说明
get() 阻塞直到结果就绪，返回结果。只能调用一次，调用后 valid() 变为 false
wait() 阻塞直到结果就绪，但不取走结果
wait_for(d) / wait_until(t) 最多等待一段时间 / 等到某个时间点，返回 std::future_status，包含 ready、timeout 等等
valid() 判断是否关联着共享状态，即当前是否还能调用 get()
share() 把共享状态转交给 std::shared_future，此后自身不再有效

std::future<T> 的结果类型为 T，即 get() 返回 T，调用 get() 后 future 失效，共享状态被释放，因此共享状态中的结果实际上会被移动出来，不会产生拷贝开销。future 还有两个模板特化。其中 std::future<T&> 特化返回 T&，std::future<void> 特化无返回值。另外还有两点：① get() 只能调用一次，get() 后共享状态被释放，valid() 变为 false，多次 get() 会抛 std::future_error；②任务内部抛出的异常会存入共享状态，直到调用 get() 时在调用线程中重新抛出，所以比线程更加安全。

std::shared_future 主要用于多个线程需要读取同一个异步结果，因为 std::future 不可拷贝，因此一个结果默认只能被一个线程取走。若需要让多个线程都能读取同一个结果，可以用 share() 把它转成可拷贝的 std::shared_future，多个线程各自持有一份副本，这样就都能调用 get() 取到相同的值。或者通过同一个 std::shared_future 多次调用 get()，这样并不会使自身失效，只是 get() 返回的是 const T&，而不是移动出值。

promise

跨线程间的通讯可以由一对 std::promise 和 std::future 处理，二者是同一份共享状态的两端：future 是结果的读取端，promise 是结果的写入端。使用 std::promise<T> 的 get_future() 可以取出与之关联的 std::future<T>，此后任意线程都能通过 promise 显式写入结果或异常，写入的同时共享状态变为就绪，等待在 future 上的线程随即被唤醒并取走结果。promise 把结果什么时候产生由谁产生完全交给调用者决定，因此适合结果并非某个函数返回值、或需要跨回调传递结果的场景。std::promise 不可拷贝、只能移动，因此常常通过移动把它交给产生结果的那个线程。其常用的成员函数如下：

并行算法

C++ 17 起，<algorithm>、<numeric> 中的许多经典算法增加了接受执行策略 execution policy 的重载，可以把串行执行的算法改为并行执行，执行策略本身定义在 <execution> 头文件中。C++17 引入了三种标准执行策略，C++20 又增加了一种：

执行策略 说明
std::execution::seq 串行执行，不允许并行与向量化（默认策略）
std::execution::par 允许并行执行，但同一线程内对元素的调用按顺序执行，不会交错
std::execution::par_unseq 允许并行执行，且同一线程内对元素的调用可交错执行，通常用于启用 SIMD/向量化
std::execution::unseq 不并行执行，但允许对元素的调用交错执行，通常用于启用 SIMD/向量化（C++ 20 起）

向量化 vectorization 可以理解为让 CPU 用一条指令同时处理多个数据，通常依靠 CPU 的 SIMD 指令实现。

另外，执行策略只是允许而非强制并行，标准并不要求算法真的并行执行，实现完全可以合法地退化为串行。即便是在支持并行的实现上，实际并行化也还需要标准库实现提供相应的并行后端，若所用实现没有提供该后端（如 libstdc++ 需要额外链接 TBB），那么传入 par 等策略后算法可能被静默忽略，仍然串行执行，因此使用前应确认所用实现是否支持并行算法。
