第十二章 异常处理和预处理指令

异常处理

异常处理 exception handling 是一种用于处理程序运行时错误或异常情况的机制。它允许程序在遇到错误时，比如除零、数组越界、内存分配失败、打开不存在的文件等，将控制权从错误发生的地方，转移到专门处理该错误的代码处，从而将异常检测与异常处理分离开来。

异常处理相关的关键字有 try、catch、throw：
①throw 表达式：当检测到错误时，使用 throw 来抛出一个异常。可以抛出任何类型的对象，如内置类型、字符串或自定义类对象，以传递错误信息，但实践中建议抛出从标准异常类派生的对象（详见后面的标准异常类小节）；
②try-catch 语句块：用于捕获并处理对应类型的异常。try 语句块以关键字 try 开始，并以一个或多个 catch 子句结束。try 语句块中代码抛出的异常通常会被某个 catch 子句（也称为异常处理器 exception handler）捕获并处理。

栈展开

当抛出一个异常后，即执行到 throw 时，程序会暂停当前函数的执行过程并立即开始寻找与异常匹配的 catch 子句。当 throw 出现在一个 try 语句块内时，会检查与该 try 块关联的 catch 子句。如果找到了匹配的 catch，就使用该 catch 处理异常。如果这一步没找到匹配的 catch 且该 try 语句嵌套在其他 try 块中，则继续检查与外层 try 匹配的 catch 子句。如果还是找不到匹配的 catch，则退出当前的函数，在调用当前函数的外层函数中继续寻找。若最终还是找不到匹配的 catch 时，程序将调用标准库函数 std::terminate 终止程序的执行。

一旦系统找到匹配的 catch 处理器，程序的控制权会从抛出点跳转到 catch 块。但在跳转之前，所有位于 try 块开始处到异常抛出点之间、已经构造完成但尚未销毁的局部对象，都会被按照构造的逆序自动调用其析构函数进行销毁，这一过程称为栈展开 stack unwinding。

栈展开与析构函数

在 C++ 11 之后，所有析构函数默认被隐式声明为 noexcept，这意味着如果在析构函数中抛出了异常，且该异常没有被捕获（即逃逸出析构函数体），程序会立即调用 std::terminate 终止。然而，我们仍然可以显式地将析构函数声明为 noexcept(false)，告诉编译器该析构函数允许抛出异常，编译器不会再强行终止程序。

但即使如此，如果栈展开正在进行（即已经有一个未处理的异常），此时若析构函数又抛出了新的异常，会导致同时存在两个活动异常，此时 C++ 运行时将立即调用 std::terminate() 强制终止进程。如果析构函数在正常流程（非栈展开）中被调用，抛出不会立即终止程序，但通常仍不建议，因为无法预测其是否会发生在栈展开期间。

同时，很难在析构函数里安全地处理异常，因为析构函数的主要职责是释放资源，如果释放操作本身有异常，此时抛出异常去处理这个错误时，往往更加危险。另外，函数中负责释放资源的部分代码也有可能会被跳过。所以，为了程序的健壮性，不要让析构函数抛出异常。

异常对象

异常对象 exception object 是 throw 表达式创建的特殊临时对象，它的类型在编译时由 throw 的操作数决定，被存储在特殊内存区域中（通常是堆，但标准未强制指定），从而独立于当前调用栈（栈展开时不会销毁它）。当异常处理完毕后，异常对象被销毁。

异常对象的类型必须是一个完全类型，即在编译时编译器就能知道它占多大内存以及它的内部结构。并且该类型由 throw 的操作数表达式的静态编译时类型决定，如果一条 throw 表达式解引用一个基类指针，而该指针实际指向的是派生类对象，则抛出的对象将被切掉一部分，只有基类部分被抛出。如果操作数是数组或函数类型，会进行数组到指针或函数到指针的隐式转换，因此抛出的实际类型是指针类型。

异常对象的初始化与操作数的值类别紧密相关：①若操作数是纯右值 prvalue，异常对象直接从该纯右值构造（强制复制省略 guaranteed copy elision，C++17 起），此时不会调用拷贝或移动构造函数；②若操作数是左值 lvalue，使用拷贝初始化，即调用拷贝构造函数；③若操作数是将亡值 xvalue，优先使用移动构造函数，否则回退到拷贝构造。

当 throw 的操作数是本函数的局部变量（且满足返回值的移动条件）时，该左值会被视为右值（将亡值 xvalue）来处理，这被称为隐式移动。

除了承诺不会抛出异常外，noexcept 还有其它两方面的作用：
①性能优化：编译器知道函数不会抛异常后，可以省略与栈展开相关的异常处理开销，生成更高效的代码；
②移动语义保证：能让标准库容器在操作时更高效，以 std::vector 扩容为例，当 vector 容量不足时，需要重新分配更大的内存并转移旧元素。如果元素的移动构造函数是 noexcept，vector 可以安全地使用移动操作，如果移动构造函数不是 noexcept，vector 为了保证强异常安全，只能退而使用拷贝操作。

预处理指令

预处理指令 preprocessor directive 是源代码中以 # 开头的指令，它们由预处理器 preprocessor 在编译之前进行处理。C++ 从源代码到可执行文件，大致要经过预处理 preprocessing -> 编译 compiling -> 链接 linking 三个阶段，预处理器在编译器真正开始分析语法之前，对源代码进行机械的、文本层面的变换，主要包括以下几种操作：
①宏替换：将 #define 定义的宏按照规则展开成对应的替换文本；
②条件编译：根据 #if、#ifdef 等指令的条件判断结果，决定哪些代码被保留、哪些被丢弃；
③文件包含：将 #include 指定的头文件内容原样插入到指令所在的位置；
④其它：删除注释、处理 #line、#pragma、#error 等指令。

预处理器处理完成后再将结果交给编译器进行语法分析和编译，所以预处理指令既不是语句也不是表达式，它们的语法不遵循 C++ 的语法规则，不需要以分号结尾，也因此容易引发各种问题。

命名空间

大型程序往往会使用多个独立开发的库，这些库又会定义大量的全局名字，如类、函数和模板等。当应用程序用到多个供应商提供的库时，多个库将名字放置在全局命名空间中，不可避免地会发生某些名字相互冲突的情况。而命名空间 namespace 是对全局作用域进行切分的一种机制，每个命名空间是一个作用域，它把一组全局范围内的标识符（变量、函数、类等）组织到一个具名的作用域容器中，从而限定这些名字的可见范围，从而避免命名冲突。

源文件

大型程序通常不会把所有代码塞进一个文件中，而是拆分成多个源文件 source file（通常以 .cpp 结尾）与头文件 header file（通常以 .h 或 .hpp 结尾）共同组织，将接口（函数声明）和实现（函数定义）分离开来。

编译流程

C++ 的编译流程可以细分为以下三个步骤：
①预处理 preprocessing：由预处理器对每个源文件独立进行文本层面的变换，包括宏展开、#include 文件包含、条件编译、删除注释等，预处理的结果被称为翻译单元 translation unit；
②编译 compiling：编译器将预处理后的结果逐条翻译为机器码，生成对应的目标文件 object file。目标文件中除了机器码，还包含一份符号表 symbol table，记录当前文件中定义或引用的名字（函数、全局变量等）及其地址信息；
③链接 linking：链接器收集所有的目标文件以及用到的库，根据各文件的符号表把相互引用的符号解析并拼接起来，最终生成一个完整的可执行文件 executable file。

整个流程可以简单示意如下：

math.cpp  ──预处理──► 翻译单元 ──编译──► math.obj  ─┐
main.cpp  ──预处理──► 翻译单元 ──编译──► main.obj  ─┴──链接──► program.exe

每个源文件（每个翻译单元）都是独立编译的，编译器在编译某个 .cpp 文件时，看不到其它 .cpp 文件中的任何内容，只能看到当前文件中通过 #include 引入的头文件以及本文件内的声明。也正因为如此，声明与定义必须分离：声明可以重复出现，而定义在一个程序中只能出现一次，真正的定义由链接器在链接阶段统一解析。

翻译单元

翻译单元 translation unit（有时也称编译单元）是一个源文件经过预处理之后得到的结果，也就是 #include、宏展开等预处理指令全部处理完毕、可以被编译器直接进行语法分析的那份代码。一个翻译单元通常由一个 .cpp 源文件及其 #include 的所有头文件内容拼接而成，每个翻译单元都会被独立地编译成一个目标文件。

声明与定义

声明 declaration 的作用是告诉编译器某个名字的存在以及它的类型（例如函数的返回类型和参数列表），定义 definition 则不仅声明名字，还会为变量分配存储空间，或为函数提供函数体。二者的关键区别在于：
①声明可以在一份程序中重复出现多次，只要类型一致即可；
②定义在一份程序中通常只能出现一次，C++ 通过单一定义规则 One Definition Rule (ODR) 来约束这一点，违反该规则（例如同一函数在多个目标文件中都有定义）会导致链接错误。

之所以头文件里放声明、源文件里放定义，正是因为声明可以被多个翻译单元反复包含而不会出错，而定义一旦被包含进多个翻译单元，链接时就会产生重复定义错误。

链接属性

链接属性 linkage 描述了名字在不同翻译单元之间是否可见、能否被引用，分为两种：
①外部链接 external linkage：默认情况，拥有外部链接的名字可以被其它翻译单元通过声明（如 extern）访问，链接时由链接器解析这些跨文件的引用。具有外部链接的名字在整个程序的所有翻译单元中都可见且唯一，所有翻译单元共享同一个实体；
②内部链接 internal linkage：拥有内部链接的名字只在当前翻译单元内可见，其它翻译单元无法访问，如果另一个 .cpp 文件有相同名字，它们互不干扰，各自独立。常见的具有内部链接的情况有：文件作用域的 const 变量、static 修饰的全局变量或函数、匿名命名空间中的成员（见命名空间一节）等。

头文件

头文件 header file 用来集中存放声明，其核心价值在于共享接口：当多个源文件都需要使用同一批函数、类时，不必在每个文件中重复书写声明，只需 #include 同一个头文件，同时也避免了不同文件间声明不一致的问题。头文件与源文件的分工一般是声明放头文件，定义放源文件，具体来说：
①函数：头文件中放函数声明，源文件中放函数定义；
②类：类的定义（成员变量与成员函数的声明）放在头文件中，成员函数的实现放在源文件中。类定义是一种声明性质的实体，多个翻译单元包含同一个类定义并不违反 ODR；
③模板：模板的定义必须放在头文件中，因为模板要等到实例化时才生成代码，编译器必须看到完整的模板定义才能实例化；
④常量：文件作用域的 const 变量默认具有内部链接，可以直接放在头文件中，每个包含它的翻译单元各自持有一份拷贝，不会引起重复定义；
⑤inline：inline 修饰的函数（或 C++17 起的变量）可以定义在头文件中。因为它豁免了 ODR（单一定义规则），允许在多个翻译单元中出现相同的定义。链接器最终会保留其中一份定义（进行去重处理），而不会因多份定义报错。

链接

链接 linking 是编译流程的最后一步，负责把多个目标文件拼接成一个可执行文件。除了拼接自己编译出的目标文件外，实际开发中程序还经常要使用别人预先编译好的库 library，库中打包了一系列函数的目标代码，例如 C++ 标准库、第三方库等。根据链接器处理这些库的方式不同，链接可以分为静态链接 static linking 和动态链接 dynamic linking 两种，这也是程序分发部署时需要考虑的重要问题。

注意：这里讨论的链接是指编译流程中的链接阶段，即链接器如何把目标文件与库组合成可执行文件，注意与翻译单元小节介绍的链接属性 linkage 进行区分。

①静态链接 static linking：在链接阶段就把库中用到的那部分目标代码直接复制、整合进最终的可执行文件中，对应的库称为静态库 static library，在 Windows 下是 .lib 文件，在 Linux 下是 .a 文件。静态链接完成后，可执行文件是自包含、完整的，运行时不再需要依赖任何库文件，但是体积较大。

②动态链接 dynamic linking：在链接阶段并不把库代码复制进可执行文件，只记录程序用到了哪些符号（函数名、参数类型等），在可执行文件中留下对库函数的引用占位符，真正解析和加载库代码的工作推迟到程序运行时，由操作系统与动态链接器 dynamic linker 完成。对应的库称为动态库 dynamic library，在 Windows 下是 .dll 文件（Dynamic Link Library 的缩写），在 Linux 下是 .so 文件，在 macOS 下是 .dylib 文件，因此动态库也常被称为共享库 shared library。动态链接的最终产物是一个较小的可执行文件加上若干个动态库文件。

一个程序可以同时使用静态链接与动态链接：把必须稳定可靠的代码静态链接进程序，把可共享、需要频繁更新的部分（如标准库、系统库、插件）做成动态库，这也是大多数 C/C++ 程序的实际组织方式。

模块

模块 module 是 C++ 20 引入的一种全新的代码组织方式，与传统的头文件 + 源文件相比，模块可以解决一些问题，比如：
①显著提升编译速度：头文件在每一个包含它的 .cpp 文件中都会被重复解析和编译。而模块只编译一次，编译结果会存储在二进制文件中，再次导入时直接使用，速度极快；
②更好的封装性与隔离性：在模块中，只有显式导出的内容（类、函数等）才对导入方可见。宏定义、未导出的内部实现细节和私有声明都被封装在模块内部，不会污染全局命名空间，也避免了宏重定义和命名冲突问题；
③消除头文件顺序依赖：传统头文件的包含顺序可能影响编译结果，模块的导入顺序无关紧要。

由于模块至今（C++20 / C++23）在各编译器中的支持程度仍不完全一致，且尚不成熟，属于相对较新的特性，本笔记仅对其核心概念做基础介绍。

基本语法与概念

模块主要涉及三个核心关键字：module 用于声明一个模块单元，export 用于将模块中的声明标记为公开，import 用于在一个翻译单元中导入并使用一个模块单元。一个模块由若干个模块单元 module unit 组成，每个模块单元对应一个翻译单元（一个 .cpp 源文件），按照作用分为两类：
①模块接口单元 module interface unit：以 export module 模块名; 声明开头，定义模块的对外接口，只有这里的实体可以被导出。通常扩展名是 .ixx（MSVC）或 .cppm（Clang / GCC）；
②模块实现单元 module implementation unit：以 module 模块名; 声明开头，提供模块的内部实现，不导出任何实体。实现单元常用扩展名也是 .cpp。

定义模块接口

在模块接口单元中，只有带 export 关键字的声明才对模块外部可见，export 可以修饰函数、类、变量、模板、命名空间等：
①export 声明：直接在声明前加 export，如 export int add(...)、export class Vector {...}、export namespace tools {...}；
②export 块：用 export { ... } 一次性导出多个声明，写法更整洁；
③未加 export 的声明：在模块内部可见（作为实现细节），但模块外部无法使用。

标准模板库 STL

标准模板库 standard template library (STL) 是标准库中最著名、最常用的一部分，它并非标准库的全部，而是特指其中以模板为基础的泛型组件集合。STL 将存储数据的容器（数据结构）、访问数据的迭代器与处理数据的算法三者解耦，再通过函数对象与适配器把它们灵活组合，从而可以用同一套通用算法处理不同类型的数据结构。STL 拥有六大组件，分别是容器 containers、算法 algorithms、迭代器 iterators、函数对象 function objects、适配器 adapters 和分配器 allocators：

①容器 containers：用来存储和管理数据的类模板，如 std::vector、std::map 等。容器封装了数据的存储布局、扩容与释放等细节，是数据结构的现成实现；
②算法 algorithms：用来处理数据的泛型函数模板，如 std::sort、std::find 等。算法不直接操作容器，而是通过迭代器间接访问元素，因此同一套算法可以适用于所有提供相应迭代器类别支持的容器；
③迭代器 iterators：用来遍历和访问数据的统一接口，使得同一个算法可以操作不同类型的容器；
④函数对象 function objects：重载了函数调用运算符 operator() 的类对象，可以像函数一样被调用，却能携带状态，常作为算法行为的定制参数传入（如排序规则、查找条件）；
⑤适配器 adapters：用于将一种容器或迭代器适配成另一种容器或迭代器，以满足特定的需求，常见的有容器适配器（如 std::stack、std::queue）、迭代器适配器（如反向迭代器、插入迭代器）等；
⑥分配器 allocators：负责为容器分配和释放内存的组件。绝大多数情况下我们使用容器的默认分配器即可，但在需要对内存分配进行精细控制（如使用内存池）的特殊场景下，也可以自定义分配器。

初始化器列表 initializer_list 是 C++ 11 引入的一种标准库类型，定义在头文件 <initializer_list> 中，它是一个轻量级的代理对象，并不真正存储元素，而是提供对一段底层元素数组的只读访问，由此提供了一种统一便捷的方式来访问由花括号 {} 包围的值列表，标准库通常将其实现为一对指针（指向首元素和尾后元素）或一个指针加一个长度。标准库容器（如 std::vector、std::map 等）之所以可以直接用 {} 初始化，正是因为它们都提供了接受 std::initializer_list 的构造函数。

std::initializer_list 值得注意的一些特性如下：
①元素只读：initializer_list 中的元素类型是 const T，只能读取不能修改，因此无法通过它修改底层数组中的元素；
②底层数组的生命周期：使用花括号列表构造 initializer_list 时，例如 {1, 2, 3}，编译器会创建一个临时数组 const int[3] 来存放这些元素，该临时数组的生命周期与整个 initializer_list 表达式一致；
③拷贝是浅拷贝：拷贝或赋值一个 initializer_list 对象，只是复制了它指向底层数组的指针，并不会拷贝元素本身，因此拷贝开销极小；
④空花括号的二义性：{} 存在歧义，例如 std::vector<int> v{}; 会优先调用默认构造函数（构造空 vector），而不会解释为空的 initializer_list。若想显式调用空的 initializer_list 版本，需要写成 std::vector<int> v({});。

容器

容器 container 是 STL 中最常用的组件，是一类存储和管理数据集合的类模板。根据元素的组织方式与访问模式的不同，标准库容器大致可以分为四类：

①顺序容器 sequence container，按特定顺序存储元素，该顺序由插入位置决定，与元素的值无关：
   - std::array：固定大小数组。大小固定，编译时确定，内存连续，访问高效，用于替代 C 风格数组；
   - std::vector：动态数组。可自动扩容，内存连续，是最常用的容器选择。尾部插入/删除 O(1)，中间插入/删除 O(n)，随机访问 O(1)；
   - std::deque：双端队列。内部采用分段连续存储，但整体内存不连续。两端均可高效插入/删除 O(1)，中间插入/删除 O(n)，随机访问 O(1)；
   - std::list：双向链表。内存不连续，较高的内存与遍历开销。不支持随机访问，已知迭代器位置插入/删除 O(1)；
   - std::forward_list：单向链表。比 list 更节省内存，但只能单向遍历，不支持尾部操作，不支持随机访问。

②关联容器 associative container，元素按键 key 自动排序存储，通常基于红黑树实现，查找、插入和删除的时间复杂度均为 O(log n)：
   - std::set：集合。唯一键的集合，元素既是键也是值，自动按值排序，元素唯一且不能修改；
   - std::multiset：多重集合。允许键重复的集合，其它类似 std::set；
   - std::map：映射。键值对集合，键唯一，自动按键排序，键唯一且不能修改；
   - std::multimap：多重映射。允许键重复的键值对集合，其它类似 std::map。

③无序关联容器 unordered associative container，元素按键 key 哈希存储、不保证顺序，基于哈希表实现，平均情况下查找、插入和删除的时间复杂度均为 O(1)：
   - std::unordered_set：无序集合。元素（键）唯一且无序；
   - std::unordered_multiset：无序多重集合。允许元素（键）重复；
   - std::unordered_map：无序映射。存储键值对，键唯一，元素无序；
   - std::unordered_multimap：无序多重映射。存储键值对，允许重复键，元素无序。

④容器适配器 container adaptor，并不是独立的容器，而是基于其它容器封装出受限接口的类模板，只能通过其提供的接口访问元素，不支持迭代器：
   - std::stack：栈。后进先出 LIFO，只能在栈顶压入 / 弹出元素，默认基于 std::deque 实现；
   - std::queue：队列。先进先出 FIFO，队尾入队、队头出队，默认基于 std::deque 实现；
   - std::priority_queue：优先队列。按优先级出队，优先级最高的元素最先出队，默认基于 std::vector 实现。

扩容机制

std::vector 通过大小 size（当前元素个数）和容量 capacity（已分配内存能容纳的元素总数）两个概念来管理内存。当 size 与 capacity 相等时，意味着当前分配的内存已经用完。此时，若再进行任何增加元素的操作，如 push_back()、insert()、emplace() 等，就会触发扩容 reallocation，其过程通常包括以下步骤：

  1. 分配新内存：在堆上分配一块新的、更大的连续内存空间。容量通常遵循几何增长的策略，即每次扩容后的新容量是当前容量的一个固定倍数，GCC 和 Clang 通常采用 2 倍扩容，MSVC 通常采用 1.5 倍扩容。
  2. 迁移元素：将旧内存中的所有元素，逐个拷贝或移动到新内存中。在 C++ 11 之前，只能进行拷贝构造，自 C++ 11 开始，若元素的移动构造函数是 noexcept 的，则会优先使用更高效的移动构造，否则，为保证异常安全，会退回到拷贝构造。
  3. 销毁并释放旧内存：按顺序调用旧内存中所有元素的析构函数，然后释放原来的整个内存块。
  4. 更新内部状态：将 vector 内部的指针更新为指向新内存，并更新 capacity 和 size 的值。

迭代器失效

由于 std::vector 的底层是连续内存，任何改变元素个数或触发扩容的操作，都可能导致元素在内存中的位置发生变化，从而使之前获得的迭代器、引用和指针不再指向原来的元素。对失效的迭代器进行解引用、递增或递减等操作都是未定义行为，可能导致程序崩溃或产生难以预料的结果。

具体来说，使 vector 的迭代器失效的操作可以分为两类：
①使所有迭代器、引用和指针失效的操作：主要是触发扩容的操作，因为扩容会分配新内存并把所有元素搬移到新地址，旧位置上的任何迭代器、引用和指针都会失效。这类操作包括：在 size == capacity 时进行的 push_back、insert、emplace、emplace_back，以及 reserve（当新容量大于当前容量时）、resize（当扩大且超出容量时）和 shrink_to_fit（请求缩减容量时）等；
②使部分迭代器失效的操作：插入或删除元素本身虽然不改变元素的内存地址，但插入点或删除点之后的元素会被搬移，因此会使其后所有迭代器、引用和指针失效。例如中间位置的 insert 和 erase，以及 pop_back（使指向被删除尾元素的迭代器失效）。

迭代器失效是编写容器代码时最容易踩的坑之一，常见的规避手段是：①每次修改容器后都重新获取迭代器；②利用 insert / erase 返回的新迭代器继续遍历。

底层原理

std::unordered_map 的底层是哈希表，GCC、Clang、MSVC 均采用分离链接法/链地址法 separate chaining 来处理哈希冲突。其内部维护一个桶数组 bucket array，每个桶都关联着一个链表 linked list，用于存储所有哈希到该桶的元素。当插入一个键值对时，用一个哈希函数 hash function 把键映射为一个整数，即哈希值，再通过对桶数量取模得到目标桶的索引，将元素放入桶数组中的某个桶内，同一个桶中的多个元素再以链表形式串起来。整个结构涉及以下几个核心概念：

  • 哈希函数 hash function：容器通过 std::hash<Key> 函数对象为键计算哈希值。内置类型（如 int、double）与常用类型（如 std::string）在标准库中都有默认的 std::hash 特化；自定义类型需要用户提供 std::hash 特化或自定义的哈希函数对象，否则无法用作 unordered_map 的键；
  • 桶 bucket：桶数组是一块连续存储的数组，每个桶对应一条链表。键的哈希值对桶数量取模后，得到该键所属的桶下标，元素便挂在该桶的链表上；
  • 哈希冲突 hash collision：不同键的哈希值可能相同，或对桶数取模后落入同一个桶，这种现象称为哈希冲突；
  • 负载因子 load factor：定义为元素个数与桶数量的比值 size / bucket_count，反映哈希表的拥挤程度。当负载因子超过 max_load_factor（默认为 1.0）时，容器会自动增加桶的数量并重新散列所有元素，这一过程称为重哈希 rehash 。

实际实现中通常不会为每个桶单独维护一个独立的 std::list 对象，而是使用一个全局的双向或单向链表来存储所有的元素节点，桶的数组中存储的是指向这个全局链表中特定位置的指针。这样做遍历整个 unordered_map 时，只需遍历这个全局链表，无需跳过空桶，保证了 O(n) 的遍历复杂度。

桶与重哈希

底层原理小节中提到过，重哈希 rehash 的触发由负载因子 load factor（size / bucket_count）控制，当元素个数增加导致负载因子超过 max_load_factor（默认值是 1.0）时，容器会重新分配更大的桶数组，并把所有元素按新桶数重新散列，步骤如下：

  1. 申请新内存：根据增长策略计算出更大的桶数量，并分配新的桶数组。GCC 按质数递增，Clang/MSVC 则采用 2 倍扩容；
  2. 遍历旧桶重新计算哈希：遍历旧桶数组中的每一个链表上的节点 node，重新计算每个元素的哈希值，确定该元素在新桶数组中的目标位置；
  3. 转移节点：将旧节点从旧链表中解链，头插或尾插到新桶对应的链表中，整个过程只移动指针，不会对元素的 key 和 value 进行任何拷贝或移动构造。
  4. 析构旧桶数组：析构并释放旧桶数组，更新容器内部的元数据，bucket_count 更新为新值， max_load_factor 不变，size 不变。

迭代器失效

std::unordered_map 的迭代器稳定性比 std::vector 好得多：
①插入和删除（不触发重哈希）：insert、emplace、erase 等操作不会使任何迭代器、引用、指针失效（指向被删除元素除外），因为元素在桶链表中的位置不因其它元素的操作而改变；
②重哈希 rehash：只有触发重哈希的操作，包括 rehash、reserve，或插入后负载因子超限，会使所有迭代器失效，因为所有元素都被搬移到新桶中。但指向元素的引用和指针仍然有效，因为元素对象本身并未被搬移，只是它们所属的桶改变了。

迭代器

【书签】

迭代器 iterator 是 STL 中用来遍历和访问容器元素的统一接口，它抽象出了”指向某个元素、并能移动到下一个元素”的能力，从而把算法与容器解耦：算法只通过迭代器操作数据，不关心数据存储在哪种容器中。迭代器相关组件定义在头文件 <iterator> 中，可以把它理解为一个广义的指针——对 std::vector 这类内存连续的容器，其迭代器通常就是底层指针的封装；而对 std::list、std::unordered_map 等容器，迭代器则是内部节点的抽象。

每个容器都通过 begin() / end() 等成员函数返回自己的迭代器，其中 end() 返回指向容器最后一个元素之后的尾后迭代器 past-the-end iterator，它不指向任何元素，通常作为遍历的终止条件。

迭代器的基本操作

所有迭代器都支持一系列统一的操作，常用的如下：

操作 说明
*it 解引用，返回迭代器指向的元素的引用
it->member 箭头运算符，等价于 (*it).member，访问元素的成员
++it / it++ 前置 / 后置递增，移动到下一个元素
it == it2 / it != it2 比较两个迭代器是否相等 / 不等
--it 前置递减，移动到上一个元素（双向 / 随机访问迭代器）

it1 - it2 返回两个迭代器之间的距离（随机访问迭代器）

迭代器分类

标准库根据迭代器支持的操作能力，把迭代器划分为五种类别，能力从弱到强依次是：输入迭代器、输出迭代器、前向迭代器、双向迭代器和随机访问迭代器：

迭代器类别 支持的操作 典型例子
输入迭代器 input iterator 只读遍历，支持 *it、++it、判等，单向移动 std::istream_iterator
输出迭代器 output iterator 只写遍历，支持 *it = x、++it，单向移动 std::ostream_iterator
前向迭代器 forward iterator 同时支持读写，可多次遍历，单向移动 std::forward_list、std::unordered_map 的迭代器
双向迭代器 bidirectional iterator 在前向迭代器基础上支持 --it 反向移动 std::list、std::set、std::map 的迭代器
随机访问迭代器 random access iterator 支持 it + n、it - n、下标访问、关系比较，可任意跳跃 std::vector、std::deque、std::array 的迭代器

算法通常要求迭代器至少具备某一类别的能力。例如 std::sort 要求随机访问迭代器，因此只能用于 std::vector、std::deque 等容器，而不能用于 std::list（std::list 提供了自己的 sort 成员函数）；std::find 只需输入迭代器，几乎可用于所有容器。

const 迭代器与反向迭代器

除了普通迭代器，容器还提供了两类常用的特殊迭代器：

①const 迭代器 const_iterator：只读迭代器，不能通过它修改元素，可通过 cbegin()、cend() 获取。当通过 const 引用访问容器时，begin() 也会返回 const 迭代器；
②反向迭代器 reverse_iterator：从容器尾部向前遍历，通过 rbegin()、rend() 获取。反向迭代器上的 ++ 在逻辑上是向容器头部移动，rbegin() 指向最后一个元素，rend() 指向第一个元素之前的位置。

迭代器适配器

迭代器适配器 iterator adapter 是在已有迭代器基础上派生出新功能的类模板，定义在 <iterator> 头文件中，常见的有三种：

①插入迭代器 insert iterator：向迭代器赋值时，会把值插入到对应容器中而不是覆盖元素，常用于配合 std::copy 等算法向容器添加元素。包括 std::back_inserter（尾部插入）、std::front_inserter（头部插入，仅支持 push_front 的容器）和 std::inserter（指定位置插入）；
②反向迭代器 reverse iterator：把迭代器的遍历方向反转，rbegin() / rend() 返回的正是这种适配器；
③流迭代器 stream iterator：把输入输出流当作迭代器使用，使算法可以直接从流中读取数据或向流写入数据。std::istream_iterator 用于读取输入流，std::ostream_iterator 用于写入输出流。
